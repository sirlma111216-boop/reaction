# 결정 기록

구현 프롬프트에 없거나 애매한 부분에서 세운 가정과, 시뮬레이션으로 바꾼 수치를 적는다. 날짜는 2026-10-09.

## 가정

- **참고 저장소 위치**: `../react-reference` 대신 작업용 임시 폴더에 얕게 클론해 읽기만 했다. 프로젝트 상위 폴더(OneDrive)에 다른 저장소를 두지 않기 위해서다. 가져온 것: 방·플레이어·팀 관리와 WebSocket Hibernation, 명령 중복 방지, 재접속, 만료, 시드 난수, 클라이언트 연결·세션·소리·그림 로더, 시뮬레이터·밸런스 CLI 의 구조.
- **긴급 지원 시점**: 정산 순서(9.2-8)에는 긴급 지원이 없어서, 「매일 아침」(3.7)에 맞춰 날짜 +1 → 하룻밤 음식 완성 **→ 긴급 지원 →** 새 손님 순서로 두었다. 손님 생성은 코인을 보지 않으므로 결과에 영향이 없다.
- **M11 「두 배로 넣는다」의 재료**: 4.3 표의 재료 수량(탄산수소 나트륨 1)을 그대로 차감한다. 재료 구성은 바꾸지 않기로 한 항목이라 2개를 차감하지 않았다.
- **M05 「데우지 않는다」의 장비**: 전기 요금은 0 이지만 메뉴 자체는 미니 오븐이 있어야 만들 수 있다(4.3 표의 장비 열을 메뉴 단위로 적용).
- **M09 의 (실패) 결과 두 개**: 두 선택지의 「왜 그럴까?」 문장이 다르므로 결과 키를 `none` 과 `none2` 로 나누었다. 결과 이름은 둘 다 「결정이 거의 없는 막대」로 같다.
- **M08 순서 선택지**: 6가지 순서를 모두 고정 ID(`syrup>milk>coffee` 등)의 선택지로 데이터에 두었다. 세 액체의 제시 순서는 (메뉴판, 날짜, 팀)으로 섞는다. 시드는 학생 화면에 보내지 않기 때문이다.
- **원리 힌트·추천은 점장이 아니어도 된다**: 힌트는 무료이고 횟수 제한이 없으며(7.4), 추천은 점장이 아닌 팀원의 기능이다. 그 밖의 팀 명령은 서버가 점장인지 검사한다.
- **장소 이동은 서버 명령이 아니다**(7.4). 참고 저장소의 `observe` 명령과 관측 기록은 가져오지 않았다.
- **결과 내보내기**: JSON 과 CSV 둘 다 `/api/rooms/<코드>/export?format=` 로 낸다. 팀 단위 기록(순위·영수증·만들기 시도·낸 음식)만 담고 개인 기록은 없다.
- **교사 로그인 제한**(9.2-4): 같은 IP 에서 1분에 10번. Directory Durable Object 의 메모리에서 센다(여러 Worker 인스턴스가 하나의 DO 를 공유하므로 한곳에서 센다).
- **교사 비밀번호가 없을 때**: `/api/teacher/login` 은 503 과 「교사 비밀번호가 설정되지 않았습니다」를 돌려준다. `/api/health` 의 `teacherReady` 로 설정 여부를 볼 수 있다.
- **단체 주문의 보너스 표시**: 카운터 게시판에 「별 3개면 팁 4 과 보너스 6」처럼 설정값을 그대로 보여 준다.
- **점장 교대**: 매일 정산 뒤 서버가 팀원 순서대로 다음 사람을 고르되, 접속이 끊긴 팀원은 건너뛴다(참고 저장소와 같음). 연습 모드는 항상 나.
- **시뮬레이션의 팀 수**: 경기당 5팀(봇 5종 × 자리 5개 순환). 처음에 6팀으로 돌렸더니 한 경기에 같은 봇이 두 자리에 서서 승률을 나눠 가져 「자리 효과」가 6%p 로 부풀려졌다. 5팀으로 바꾸자 3.0%p 가 되었다.
- **본전 회수 날의 정의**: 장비를 산 날부터, 그 장비로만 만들 수 있는 메뉴(보온 포장 세트는 포장 손님)로 번 이익(대금 − 재료비 − 전기 요금)의 누적이 장비 가격에 이르는 날까지의 날 수(산 날이 1일).
- **글꼴**: 제목 Jua, 본문 Pretendard(동적 서브셋), 손님 말풍선과 영수증 Gaegu. 모두 npm 패키지로 묶었고 CDN 을 부르지 않는다. Pretendard 동적 서브셋은 글리프 묶음 파일이 많아 CSS 가 커진다(KNOWN_LIMITATIONS 참고).
- **변화 종류·반응식 표시**: 결과별 문장(`changeKindText`, `equation`)을 데이터에 두고, 3학년·화학 반응 집중 메뉴판에서만 변화 종류를 표시한다. 반응식은 M10 `puffed`, M11 `fluffy`·`bitter`(탄산수소 나트륨을 넣은 결과), M13 `hot`, 가스레인지 카드에만 있다.

## 밸런스 조정 기록 (`src/shared/config/economy.ts` 의 `applyTuning`)

지표는 `npm run sim:validate`(검증 시드 2,000경기, 메뉴판 4종 × 영업일 3종)로 쟀다. 바꾸지 않은 것: 과학 내용, 재료 구성, 조건과 결과, 행동 수 3, 만들기 1번의 인분 2.

| 단계 | 바꾼 값 | 이유 | 전 → 후 (주요 지표) |
|---|---|---|---|
| 0 (초깃값, economy-1.0) | — | — | 1일 차 판매 100%, expert−learner 15.2%, **investor 1% vs frugal 39%(비 39)**, 본전 회수 3일, 폐기 5%, random −20 |
| 1 (economy-1.1) | 장비 메뉴 인분당 가격 +2: M01 9→11, M04 5→7, M05 7→9, M07 7→9, M11 8→10 | 하루 행동 3번이 병목이라 장비는 「만들기 1번의 이익」을 키울 때만 값어치가 있는데, 초깃값에서는 장비 메뉴와 장비 없는 메뉴의 이익이 거의 같아 장비를 사는 쪽이 늘 졌다 | investor 15% vs frugal 33%(비 2.2), expert−learner 25% |
| 2 (economy-1.2, 현재) | 장비 메뉴 인분당 가격 +1 더: M01 12, M04 8, M05 10, M07 10, M11 11 | 600경기 변형 비교(장비 −1, 장비 −2, 메뉴 +1, 전기 0, 팁 2)에서 「메뉴 +1」이 investor/frugal 비 1.3 으로 가장 좋았다 | **investor 24% vs frugal 35%(비 1.46)**, expert−learner 26.9%, 자리 효과 3.0%p, 본전 회수 2일, 폐기 3%, random −20, 지배 메뉴 M13 17% |

- 무작위 탐색(`npm run sim:balance`, 후보 1~3개 값씩 흔듦)도 두 번 돌렸지만, 작은 변화로는 장비 구조 문제를 못 고쳐 손으로 조정했다. 탐색 기록은 `reports/balance/search-history.json`.
- 봇의 승률이 비슷하다고 학생에게 재미있다는 뜻은 아니다. 사람 플레이테스트는 하지 않았다.
- 봇 정책 조정(수치가 아니라 봇 쪽): expert 는 장보기 한 번에 두 주문의 재료를 함께 사고 오늘 바로 낼 수 있는 메뉴를 먼저 만든다. 장비는 「장비 메뉴의 이익 − 장비 없는 최고 메뉴의 이익」이 남은 날 동안 장비 값을 넘길 때만 산다. investor 는 처음 3일 동안 최대 3대까지 산다(처음에는 매일 사서 행동을 다 쓰는 바람에 1일 차 판매가 0 이었다).
